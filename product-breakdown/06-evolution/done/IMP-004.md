## Evidence

- `src/cs_fmu_packager/codegen/fmi_interface.py` line 109: `"resources/%s/binaries/linux64/*.so", "{fmu_id}"`
- The generated C code uses `dlopen` with a glob pattern `*.so`, which is not a valid `dlopen` argument — `dlopen` requires the exact shared library filename.

## Current Pain Or Risk

The generated C code attempts to load an internal FMU's shared library using `"resources/%s/binaries/linux64/*.so"` with `dlopen()`. The `*` glob is not expanded by `dlopen` — it is treated as a literal character. The actual shared library filename is determined by the internal FMU's `modelIdentifier` element in `modelDescription.xml`, which may differ from the FMU's resource directory name. This means FMU loading will always fail at runtime with a "file not found" error unless the library happens to be named `*.so`.

## Proposed Improvement

At code-generation time, read each FMU's `modelDescription.xml` to extract the `modelIdentifier`, then use that identifier to construct the correct shared library path (e.g., `"resources/%s/binaries/linux64/%s.so"`). Replace the wildcard with the resolved library base name.

## Expected Benefit

Internal FMU loading works correctly at runtime. The generated C code uses the exact library path rather than depending on glob expansion that `dlopen` does not perform.

## Risk And Blast Radius

Medium. Requires parsing `modelDescription.xml` during code generation (in Python) and passing the result into the C template. The XML is already read for other purposes in `fmu_reader.py` and `model_description.py`. If `modelIdentifier` is not available or differs from the FMU's `modelDescription` standard, the fallback should be logged. The blast radius is limited to the generated `fmi2_interface.c`.
