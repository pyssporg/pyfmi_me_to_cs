## Current Pain Or Risk

1. **Redundant configuration** — Users must manually declare `[[variables]]` with `name`, `type`, `causality`, `source`, and `target` for every wrapper boundary variable. All of this information already exists in the FMU files being packaged.
2. **Fragile XML parsing** — `fmu_reader.py` uses raw ElementTree with no XML schema validation. If an FMU's modelDescription.xml deviates from the FMI 2.0 standard schema, parsing silently produces wrong results or crashes.
3. **Maintenance burden** — ~200 lines of hand-rolled FMU inspection code that duplicates the FMI 2.0 standard specification. The `pyssp_standard` package provides a maintained, schema-validated, typed API.
4. **Configuration errors** — Mismatches between spec `[[variables]]` declarations and actual FMU variables cause runtime `MappingError` exceptions that could be prevented by auto-discovery.
5. **Onboarding friction** — New users must understand the FMU variable structure AND the wrapper variable mapping format before they can write a spec. Auto-discovery reduces this to "declare your FMUs and connections."

## Proposed Improvement

Replace the custom FMU inspection in `fmu_reader.py` with the `pyssp_standard` package's `FMU` context manager, and make `[[variables]]` optional in the TOML spec. When `[[variables]]` is absent, auto-discover wrapper boundary variables directly from the FMU files.

Key changes:
1. Add `pyssp-standard` (and its transitive deps `lxml`, `xmlschema`, `pint`) to `pyproject.toml`.
2. Replace the internals of `fmu_reader.inspect_fmu()` with `from pyssp_standard.fmu import FMU` — use the `FMU` context manager to read modelDescription metadata instead of custom ElementTree parsing. Preserve the `inspect_fmu()` public API signature for backward compatibility.
3. Make `[[variables]]` optional in `spec.py` — remove from `required_sections`, keep parsing logic for backward compatibility when present.
4. When `[[variables]]` is absent, auto-discover variables by iterating each FMU's modelDescription (using `fmu.model_description.inputs`, `.outputs`, `.parameters` from `pyssp_standard`) and deriving wrapper variable entries for the mapping step.
5. Update `mapper.py` to handle both explicit (from TOML) and auto-discovered (from FMU inspection) variable sources.

**Design alternatives for auto-discovery:**
- **Option A: Expose all** — Automatically expose every input, output, and parameter from all FMUs as wrapper boundary variables. Simple but may expose many unintended variables.
- **Option B: Connection-driven** — Only expose variables that are referenced by `[[connections]]`. Requires connection syntax to allow optional source/target variable names when they differ from the matching variable (but this is already handled by the mapper).
- **Option C: Hybrid with override** — Auto-discover all variables by default, but allow a simplified `[[variables]]` entry (only `name` + `causality` required) to override naming or select a subset.

## Expected Benefit

1. **Reduced user configuration** — ~10-30 lines removed from typical TOML specs
2. **Eliminated manual variable mismatch errors** — variables come directly from FMU metadata
3. **Eliminated fragile XML parsing** — `pyssp_standard` provides schema-validated, typed FMI metadata access
4. **Simpler spec format** — fewer required sections, fewer things to go wrong for new users
5. **Leveraged community package** — benefit from upstream improvements (new FMI versions, schema updates, platform support)

## Risk And Blast Radius

- **Medium-High** — Removing `[[variables]]` as a required section breaks backward compatibility with existing TOML specs. All existing tests and documentation reference the current format.
- **Dependency risk** — `pyssp_standard` is v0.9.0 (alpha) with a small community (3 stars, 2 forks). Package may change API, become unmaintained, or have bugs.
- **Transitive dependency weight** — `lxml` (C extension, compilation needed), `xmlschema`, `pint` are non-trivial additions. `lxml` in particular may complicate CI and platform support.
- **Variable detection semantics** — Auto-discovery must decide which variables become wrapper boundary variables. Wrong heuristic causes usability frustration (too many or too few variables exposed).
- **Test refactoring** — `test_fmu_inspection.py` creates minimal inline FMU zip archives; `pyssp_standard` may require a real FMI-compliant modelDescription.xml structure. Tests may need re-creation.
- **Performance** — Opening and parsing all FMU files during spec parsing adds I/O. Could be mitigated with lazy inspection or caching.

Medium (configuration reduction benefit is high, but dependency risk and backward compatibility require careful transition planning)

## Implementation Reference

Replace `fmu_reader.py`'s custom ElementTree logic with the `pyssp_standard` FMU API:
```python
from pyssp_standard.fmu import FMU

with FMU(fmu_path) as fmu:
    md = fmu.model_description
    # Access typed variable lists:
    inputs = md.inputs       # List of ScalarVariable with causality=input
    outputs = md.outputs     # List of ScalarVariable with causality=output
    parameters = md.parameters  # List of ScalarVariable with causality=parameter
    # Access other metadata:
    md.model_identifier  # str
    md.fmi_version       # str
    md.capabilities      # FmiCapabilities
```

- Remove `[[variables]]` from `spec.py` `required_sections`; keep parsing logic for backward compatibility.
- Add auto-discovery in `mapper.py` or a new helper: when `spec.variables` is empty, derive `WrapperVariable` entries from `fmu_reader.inspect_fmu()` output.
- Update test fixtures: replace hand-crafted XML parsing tests with `pyssp_standard`-based tests using the same inline FMU zip approach (may need to adjust modelDescription.xml structure for `pyssp_standard` schema validation).
