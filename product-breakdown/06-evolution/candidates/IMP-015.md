# IMP-015: Remove dead `Jinja2` dependency and orphaned `c_templates/` Jinja files

Use this template for one backlog-ready improvement candidate.

An improvement candidate is not implementation approval. It needs a scoped task contract before code or documentation changes begin.

## Lifecycle Stage

Candidate

## Status

Proposed

## Layer

Evolution

## Theme

Dependency cleanup, dead code removal

## Evidence

- `pyproject.toml` — declares `Jinja2>=3.0` as a runtime dependency under `[project.dependencies]`
- `src/cs_fmu_packager/c_templates/` — contains 5 `.jinja` template files
- Entire `src/cs_fmu_packager/` tree — `Jinja2` is never imported or referenced
- `src/cs_fmu_packager/codegen/fmi_interface.py`, `solver.py`, `fixed_point.py` — all C code generation uses Python f-strings, not Jinja2 templates

## Current Pain Or Risk

- `Jinja2>=3.0` (~1.2 MB installed) is installed as a runtime dependency for every user but is never imported or used anywhere in the codebase
- The `.jinja` template files in `c_templates/` are never loaded, rendered, or referenced — they are dead artifacts
- A contributor reading the dependency list or the `c_templates/` directory must spend time determining whether Jinja2 is used for code generation or not, creating confusion about which codegen approach is active
- Unnecessary dependency adds attack surface, install time, and CI overhead

## Proposed Improvement

1. Remove `Jinja2>=3.0` from `[project.dependencies]` in `pyproject.toml`
2. Remove the 5 `.jinja` template files in `src/cs_fmu_packager/c_templates/`
3. If the `c_templates/` directory becomes empty, remove it as well
4. Verify no imports of `jinja2` exist anywhere in the source tree

## Expected Benefit

- Eliminates ~1.2 MB of unnecessary install burden per user
- Eliminates confusion about whether codegen uses Jinja2 or f-strings
- One less dependency to track for security updates and compatibility
- Smaller dependency tree, faster `pip install`

## Risk And Blast Radius

Minimal. Pure removal of unused code and dependency. No behavioral changes. If a future candidate (e.g., C10 re-activating Jinja2) decides to use Jinja2, the dependency can be re-added and templates re-created. The `c_templates/` directory would need to be recreated, but the current `.jinja` files are orphans that never matched the actual codegen structure, so no valuable content is lost.
