## Current Pain Or Risk

- Manual XML construction: every new test FMU requires hand-writing `modelDescription.xml` with correct FMI 2.0 schema elements, variable references, dependencies, and derivative declarations
- Fragile equation system setup: adding more complex multi-variable systems amplifies XML complexity
- Verification gap: the hand-crafted FMU's dynamic behavior is never validated against an actual compiled model — the XML describes structure, not correctness of the equation system
- Limited composability: testing interconnected systems requires manually managing multiple FMU file sets and their metadata consistency
- No behavior validation for the core ME→CS conversion: the project's main artifact (a CS FMU produced from one or more ME FMUs) has never been simulated and compared against a known-correct reference trajectory
- The existing test suite validates structural and metadata correctness but cannot catch semantic errors in the generated solver, variable mapping, or FMU assembly that produce incorrect simulation output

## Proposed Improvement

- Replace hand-crafted XML FMU generation with Modelica source files (`.mo`)
- Use the OpenModelica compiler (`omc`) to compile Modelica sources into FMI 2.0 Model Exchange FMUs
- Structure involves:
  1. Define test system equation sets as Modelica models (e.g., `Integrator.mo`, `Gain.mo`, plus compound models like `IntegratorWithGain.mo`)
  2. Script `omc` calls to export each model as an FMI 2.0 ME FMU
  3. Optionally, automate within `generate_test_fmus.py` via `subprocess` to `omc` (or a build step)
  4. Retain existing test APIs — tests consume FMU files via `fmu_fixture_path`, unchanged

### Dual-export and behavioral-verification extension

In addition to ME FMU fixture generation, extend the approach to:

5. Export compound Modelica systems as **FMI 2.0 Co-Simulation FMUs** directly from OMC (via `translateModelFMU(..., fmiType="cs")`). These serve as the "ground truth" reference for behavior comparison.
6. Run the project's own `cs-fmu-packager` ME→CS pipeline on the same compound system's ME FMU to produce a second CS FMU (the artifact under test).
7. Use **fmpy** (a pure-Python FMI 2.0 CS runtime from PyPI) to simulate both CS FMUs with identical input signals and solver settings.
8. Compare output variable time-series from both simulations using a numerical tolerance; disagreement indicates a regression or bug in the ME→CS conversion pipeline.

## Expected Benefit

1. No manual XML work — Modelica compiler handles `modelDescription.xml` generation
2. Easy equation system setup — create smaller Modelica models independently, compose into a larger verified system, then compile one FMU with the full system
3. OpenModelica compiler is readily available (Linux packages, Homebrew on macOS, Docker)
4. Behavior-verified ME→CS conversion: the core project artifact gains a repeatable, automated validation against a compiler-generated reference
5. Early regression detection: changes to the mapper, solver codegen, or FMU assembly that alter simulation behavior are caught before integration
6. Realistic test models: compound systems exercise variable connections, algebraic loops, and state propagation — scenarios the current hand-crafted fixtures cannot cover

## Risk And Blast Radius

- **Medium** — Test fixture FMU generation changes, but test code and assertions remain stable; verification tests are additive
- OpenModelica CI dependency: OMC installation must be available for fixture regeneration; may conflict with CI that currently has no OMC
- Backward compat: existing inline FMU creation in test code (`_create_minimal_me_fmu()`) still works, but the fixture-generator path changes
- OMC export fidelity: OMC may not produce identical modelDescription.xml to the current hand-crafted versions (schema structure, ordering, variable namespaces); may break `fmu_reader.py` parsing if it depends on exact element patterns
- OMC CLI flags: `omc` export requires specific flags (`--fmiFlags` for FMI 2.0 ME, `fmiType="cs"` for CS); flag documentation and version-sensitivity must be captured
- Test isolation penalty: OMC compilation adds ~seconds per FMU; cached fixtures mitigate this
- **NEW — fmpy external dependency:** Adds `fmpy>=0.3` as a test dependency. fmpy is pure-Python and well-maintained but introduces a version-sensitivity risk for FMI 2.0 CS runtime behavior. Mitigation: pin major version in `pyproject.toml` optional-dependencies, document tested version.
- **NEW — CS export flags in OMC:** OMC's `fmiType="cs"` flag may have version-specific behavior or bugs. Must document the exact OMC version used and test CS export works. Mitigation: add a pre-flight check in the generation script that verifies CS export produces a runnable FMU.
- **NEW — Comparison tolerance:** Numerical trajectories from two CS FMU simulations will not match exactly (different solver implementations, floating-point order). Must define acceptable tolerance. Mitigation: document tolerance rationale; use relative + absolute tolerance configurable per variable group; reject only statistically significant deviation.
- **NEW — CI burden increase:** fmpy install, OMC install, two FMU compilations (ME + CS) per model, plus two simulation runs. Mitigation: cached fixtures, conditional test markers (e.g., `@pytest.mark.verification` separate from `@pytest.mark.unit`).
- **NEW — pyfmi vs fmpy artifact similarity risk:** If the project itself uses pyfmi for other purposes, the verification test must ensure it compares the project's own ME→CS output against a *different* CS runtime (fmpy) to avoid same-codebase validation bias.

## Notes

- OMC FMI export reference: `omc` provides `translateModelFMU("ModelicaModelName", fmiVersion="2.0", fmiType="me")` via `.mos` scripts or interactive mode
- OMC can be installed via `apt install omc` on Ubuntu or `brew install openmodelica` on macOS
- Consider caching compiled FMUs in a `tests/fixtures/` directory and only regenerating when Modelica sources change (Makefile-based approach)
- This candidate has potential interaction with IMP-013 (pyssp_standard): OMC-generated FMUs should still be readable by `pyssp_standard` or the current `fmu_reader.py`
- fmpy reference: https://github.com/CATIA-Systems/fmpy — pure-Python FMI 2.0 CS runtime. Install via `pip install fmpy`. Provides `simulate_fmu()` which accepts start/stop time, step size, input overrides, and returns a pandas DataFrame of output trajectories.
- Comparison strategy: simulate both CS FMUs (direct OMC export + ME→CS converted) over identical time windows with identical inputs. Compare per-variable output arrays with `numpy.allclose(rtol=1e-4, atol=1e-6)` as default tolerance. Log max-deviation per variable on failure. Configurable tolerance via environment variable or test marker.
- OMC CS export reference: `translateModelFMU("ModelicaModelName", fmiVersion="2.0", fmiType="cs")` produces an FMI 2.0 CS FMU. Verify with `fmpy.fmi2.fmi2Info(fmu_path)` before simulation.
- Dual FMU lifecycle per compound model:
  1. OMC compiles compound.mo → compound_ME.fmu (for existing tests)
  2. OMC compiles compound.mo → compound_CS.fmu (ground truth reference)
  3. cs-fmu-packager wraps compound_ME.fmu → compound_from_packager.fmu (artifact under test)
  4. fmpy simulates compound_CS.fmu → reference_trajectory
  5. fmpy simulates compound_from_packager.fmu → artifact_trajectory
  6. Compare reference_trajectory vs artifact_trajectory
- This verification loop is the first automated behavioral test of the project's core ME→CS conversion pipeline. Its addition transforms the test suite from structural-only to structural + behavioral.
- Consider caching reference simulation output in a pickle/CSV file as an alternative to re-simulating the reference CS FMU on every test run. Trade-off: faster test execution but needs regeneration when OMC version changes.
