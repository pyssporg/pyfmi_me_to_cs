# IMP-025: Evaluate whether `fmpy` could replace any hand-rolled test infrastructure

Use this template for one backlog-ready improvement candidate.

An improvement candidate is not implementation approval. It needs a scoped task contract before code or documentation changes begin.

## Lifecycle Stage

Candidate

## Status

Proposed

## Layer

Evolution

## Theme

Test infrastructure evaluation, dependency leverage

## Evidence

- `pyproject.toml` — `fmpy` is already declared as an optional test dependency (used in `cs_verification.py` for behavioral verification)
- `tests/test_fmu_inspection.py` — contains manual ZIP inspection logic to read FMU metadata and `modelDescription.xml`
- `tests/fixtures/generate_test_fmus.py` — hand-crafted FMU generation logic
- `tests/test_fmu_inspection.py` — `_create_minimal_me_fmu()` creates FMUs inline via manual XML string templates

## Current Pain Or Risk

- Manual ZIP/XML inspection in tests duplicates functionality that `fmpy` already provides (e.g., `fmpy.read_model_description()`)
- Hand-rolled fixture generation duplicates work that `fmpy` could assist with (e.g., validating FMU structure)
- Test maintenance burden increases with every new test scenario that requires custom FMU creation

## Proposed Improvement

Evaluate whether `fmpy` utilities could replace or simplify:
1. The manual ZIP inspection in `test_fmu_inspection.py` — `fmpy.read_model_description()` could replace the manual `modelDescription.xml` parsing
2. Fixture generation in `generate_test_fmus.py` — `fmpy` can create minimal FMU skeletons or validate generated FMUs
3. Other test helper code that duplicates `fmpy` capabilities

## Expected Benefit

- Less hand-rolled XML/ZIP parsing code in tests
- Tests leverage a well-maintained external library instead of maintaining parallel parsing logic
- Potential to discover edge cases in `fmu_reader.py` by comparing with `fmpy`'s parsing output

## Risk And Blast Radius

**Low to moderate.**
- `test_fmu_inspection.py` tests the project's own `fmu_reader.py` implementation — replacing with `fmpy` would change what is being tested
- `fmpy` is already an optional test dependency; no new dependency required
- `fmpy` may not support all FMI 2.0 schema variations the project encounters (e.g., custom annotations, vendor extensions)

## Suggested Priority

Low (explore in future; do not pursue now)

## Traceability

- Product: `tests/test_fmu_inspection.py`, `tests/fixtures/generate_test_fmus.py`

## Notes

- `fmpy` is already used in `cs_verification.py` for behavioral simulation comparison (see IMP-014). If this candidate is pursued, the same `fmpy` dependency is leveraged more broadly.
- The key concern is test identity: `test_fmu_inspection.py` should test the project's `fmu_reader.py`, not `fmpy`. However, `fmpy` could be used as a reference parser in round-trip or differential tests.
- Consider adding a single differential test that runs both `fmu_reader.py` and `fmpy.read_model_description()` on the same FMU and asserts key fields match, without replacing the existing tests.
