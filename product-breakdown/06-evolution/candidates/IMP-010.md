## Theme

Documentation and onboarding

## Evidence

- `README.md` — empty (single heading line)
- `docs/decisions/` — architecture decision records (AD-001 through AD-006) cover design rationale but are not onboarding-oriented
- `cs-fmu-packager-project/README.md` — project-scope overview
- No single "Getting Started" or "Quick Start" document exists

## Current Pain Or Risk

Onboarding content is scattered: there is no single document that a new user can follow from zero to a working FMU. The architecture decision records are reference material, not tutorials. Users must piece together information from multiple files and the CLI `--help` output. This increases time-to-first-successful-build and discourages adoption.

## Proposed Improvement

Create a top-level `GETTING_STARTED.md` (or expand `README.md` as proposed in IMP-001 to include the same content) that provides:
1. System requirements (Python, CMake, vcpkg or system SUNDIALS, C compiler)
2. Installation instructions (`pip install .` or `pip install git+...`)
3. Quickstart: create a spec file, inspect FMUs, build, and test the output CS-FMU
4. Step-by-step walkthrough with CLI commands and expected output
5. Links to architecture decisions, example spec, and other documentation

## Expected Benefit

A new user can follow a single document from clone to working CS-FMU. The learning curve is flattened to one walkthrough.

## Risk And Blast Radius

Low. New file only. If the README is expanded (IMP-001) to include this content, a separate `GETTING_STARTED.md` may be redundant. Risk is limited to content accuracy and maintenance burden of keeping the walkthrough in sync with CLI changes.
