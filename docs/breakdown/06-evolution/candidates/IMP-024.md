## Evidence

- `src/cs_fmu_packager/c_templates/` — contains `.jinja` template stubs (currently orphaned)

- `src/cs_fmu_packager/codegen/solver.py` — ~200 lines, C code generation via Python f-strings
- `src/cs_fmu_packager/codegen/fixed_point.py` — ~149 lines, C code generation via Python f-strings
- Total ~1600 lines of f-string-based C code generation across 3 modules

## Current Pain Or Risk

- C code embedded in Python f-strings is difficult to lint, syntax-highlight, or analyze independently
- String-interpolation brittleness: mismatched braces, indentation errors, or missed escape sequences can produce invalid C that is only caught at compile time
- Reviewing generated C output requires mentally evaluating f-string expressions, which is error-prone
- Changes to C code generation require modifying Python source rather than standalone template files

## Proposed Improvement

Evaluate migrating from f-string-based code generation to Jinja2 templates:
1. Move C code templates into `.jinja` template files (one per module or per generated function)
2. Load, render, and write templates in the codegen pipeline
3. Keep the Python logic that computes variable maps, solver parameters, etc. as template context preparation
4. If successful, remove f-string codegen from the 3 modules (~1600 lines)

## Expected Benefit

- Templates can be linted and syntax-highlighted independently as C code
- Generated C is visible as plain template files; review focuses on template structure, not on string interpolation mechanics
- Adding new C code generation paths becomes a matter of adding template files rather than editing large Python modules
- Re-activates the already-declared Jinja2 dependency (see IMP-015 discussion)

## Risk And Blast Radius

**Moderate to high.**
- Refactoring ~1600 lines of codegen is a large undertaking
- Template debugging is more complex than f-string debugging (extra indirection, template inheritance, macro calls)
- Must verify byte-identical C output for all existing test cases before and after migration
- Jinja2 runtime errors surface at template render time rather than at module import time
- If IMP-015 (remove Jinja2 dependency) is implemented first, this candidate must re-add it

## Notes

- This candidate interacts strongly with IMP-015 (remove unused Jinja2 dependency). If IMP-015 is implemented first, this candidate must re-add the dependency. If this candidate is pursued instead, keep the dependency and orphaned templates.
- The evaluation should be lightweight: prototype one template, measure output, compare debugging experience. Do not commit to a full migration without evidence.
- Consider whether partial migration (e.g., solver.c only) is valuable even if the full migration is not pursued.
- F-strings remain the simplest approach for small, localized codegen. Jinja2 adds value when template files grow large or when there are multiple similar templates.
