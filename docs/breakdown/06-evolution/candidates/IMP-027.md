### Scope Definition

This candidate is the **systematic comparison** between the `cs-fmu-packager` codebase and the installed `pyssp_standard` library (upstream v0.8.2 + jkCXf9X4/pyssp_standard fork, `architecture_review` branch). It covers three categories of internal code that overlap with pyssp_standard:

1. **Graph algorithms** (connection_graph module) — upstream pyssp_standard, not fork-specific
2. **FMI model description dataclasses** (fork's typed FMI2/FMI3 model layer) — fork-specific
3. **FMU archive creation API** (FMU facade) — upstream pyssp_standard

This is **distinct** from IMP-025, which focused on fmpy + ZIP/XML parsing (lxml dual-parsing, zipfile in tests, fmpy API evaluation). IMP-027 focuses on what pyssp_standard itself already provides that the project reimplements.

### Detailed Overlap Analysis

#### Candidate A: Graph Algorithms in `mapper.py` (Direct Overlap)

**cs-fmu-packager implementation:**
- `_build_adjacency_list(connections: List[ResolvedConnection], fmu_ids: List[str]) -> Dict[str, Set[str]]`
  - Filters self-connections (`source != target`)
  - Uses `Set[str]` values (no duplicate edges)
- `_tarjan_scc(adj: Dict[str, Set[str]]) -> List[List[str]]`
  - **Recursive** implementation — risk of Python recursion limit on large FMU graphs
  - Returns `List[List[str]]` (ordered within SCC)
  - Excludes trivial SCCs (single node without self-loop)
- `_topological_sort(adj: Dict[str, Set[str]], sccs: List[List[str]]) -> List[str]`
  - Kahn's algorithm with SCC contraction + flattening
  - Handles nodes not in any SCC by adding them as singleton SCCs
- Execution ordering is done inline in `build_mapping()` (lines 339–365): SCC detection → AlgebraicLoop objects → execution_order

**pyssp_standard equivalent (`standard/operations/connection_graph.py`):**
- `build_adjacency_list(connections: list[tuple[str, str]]) -> dict[str, list[str]]`
  - Does NOT filter self-connections
  - Uses `list[str]` values (allow duplicate edges)
- `find_strongly_connected_components(adjacency: dict[str, list[str]]) -> list[set[str]]`
  - **Iterative** Tarjan's algorithm — no recursion limit
  - Returns `list[set[str]]` (unordered within SCC)
  - Excludes trivial SCCs (single node without self-loop); includes self-loops
- `topological_sort(adjacency: dict[str, list[str]]) -> list[str]`
  - Kahn's algorithm on a DAG
  - Raises `ValueError` on cycles
- `compute_execution_order(connections: list[tuple[str, str]]) -> tuple[list[str], list[set[str]]]`
  - Combined: builds adjacency → finds SCCs → topological sort of condensation DAG
  - Returns `(execution_order, algebraic_loops)` where algebraic_loops are node sets only

**Key differences:**
1. **Input type**: cs-fmu-packager uses `List[ResolvedConnection]` (dataclass with source_fmu/source_variable/source_value_reference/target_*); pyssp_standard uses `list[tuple[str, str]]` (source_name, target_name). An adapter is needed.
2. **Adjacency value type**: `Set[str]` vs `list[str]` — minor, but `list[str]` may produce duplicate edges
3. **Return type**: `List[List[str]]` vs `list[set[str]]` — set loses within-SCC ordering but ordering is not semantically meaningful for algebraic loops
4. **Algorithm safety**: cs-fmu-packager uses recursion (risk of `RecursionError` on deep graphs); pyssp_standard uses iterative stack (safe)
5. **Error behavior**: cs-fmu-packager does not raise on cycles in topological_sort (it expects SCCs to handle them); pyssp_standard's `topological_sort` raises `ValueError` on cycles — but `compute_execution_order` removes SCCs before calling `topological_sort`, so this is only relevant for direct calls
6. **Self-loop handling**: cs-fmu-packager filters `source_fmu != target_fmu`; pyssp_standard includes all connections (including self-loops, which then appear as singleton SCCs)

#### Candidate B: FMI Model Description Dataclasses in `models.py` + `fmu_reader.py` (Partial Overlap)

**Current state (post-IMP-025 fork adoption):**
- `fmu_reader.py` already uses `pyssp_standard.FMU` + fork's `Fmi2ModelDescriptionDocument` and `Fmi2ScalarVariable`
- A **conversion layer** exists: `Fmi2ScalarVariable` → project's `ScalarVariable`, `Fmi2ModelDescriptionDocument` → project's `FmuMetadata`
- The conversion handles: str→int for value_reference, str→float for start, type_attributes dict→unit field, interface_attributes dict→capabilities

**What could be replaced:**
- `models.ScalarVariable` could be replaced by `Fmi2ScalarVariable` directly if all downstream consumers accepted the pyssp_standard type
- `models.FmuMetadata` could be replaced by `Fmi2ModelDescriptionDocument` with an adapter that serves the same fields
- This would eliminate `fmu_reader.py` entirely (it would just be `Fmi2ModelDescriptionDocument` construction)

**Remaining gaps preventing full adoption:**
1. Downstream consumers (`build_mapping`, `codegen/*`, `model_description.py`) depend on `FmuMetadata.variables: Dict[str, ScalarVariable]` for by-name variable lookups — `Fmi2ModelDescriptionDocument.variables` is `list[Fmi2ScalarVariable]`
2. `ScalarVariable` has `value_reference: int`; fork's `Fmi2ScalarVariable.value_reference` is `int` for FMI2 — compatible
3. `ScalarVariable` uses `type` (reserved keyword); `Fmi2ScalarVariable` uses `type_name` — breaking difference
4. `FmuMetadata` collects `can_get_and_set_state`, `can_serialize_fmu_state`, `can_get_directional_derivative` from `interface_attributes` dict — fork's `Fmi2InterfaceAttributes` has typed fields but they may not match 1:1
5. `FmuMetadata.unsupported` is project-specific logic

#### Candidate C: FMU Archive Creation in `packager.py` (Partial Overlap)

**cs-fmu-packager implementation (`assemble_fmu`):**
- Hand-rolled ZIP creation via `zipfile.ZipFile` with custom `_make_zip_info()` for deterministic timestamps
- Writes `modelDescription.xml`, embedded `.so`, and internal ME `.fmu` files
- Uses `ZIP_DEFLATED` compression, sorted entries implicitly by write order

**pyssp_standard equivalent (`FMU` class):**
- `FMU.create(path, model_description, binaries, resources)` — creates valid FMU ZIP with FMI-standard directory structure
- `FMU.add_binary(source, platform)` — adds to `binaries/<platform>/`
- `FMU.add_resource(source, target_name)` — adds to `resources/`
- `FMU.add_model_description(source)` — adds modelDescription.xml at root

**Key differences:**
1. **Deterministic timestamps**: pyssp_standard does not offer control over ZIP entry timestamps (archive_runtime uses actual mtime). The project's NFR-001 requires reproducible artifacts.
2. **CS-specific modelDescription.xml**: The project generates its own modelDescription.xml with tool annotations; pyssp_standard would try to serialize its own document or accept a pre-built file via `add_model_description(source)` — compatible if we write the XML first.
3. **Binary embedding**: `FMU.add_binary()` uses the standard platform directory structure (`linux64`). Compatible.
4. **Resource embedding**: `FMU.add_resource()` uses the standard `resources/` directory. Compatible.
5. **Archive runtime overhead**: pyssp_standard extracts to temp directory on open and re-packages on close — adds I/O overhead compared to direct `zipfile.ZipFile` writing.

#### Candidate D: Model Description XML Generation (Partial Overlap)

**cs-fmu-packager implementation (`generate_model_description`):**
- Full XML string template generation (184 lines)
- Generates FMI 2.0 Co-Simulation modelDescription.xml with:
  - Custom `<CoSimulation>` capability flags (all false for v1)
  - `<Annotations><Annotation name="cs-fmu-packager"><CsFmuPackager ...>>` section with internal build metadata
  - `<InternalConnections>` annotation with full connection graph
  - Tool-specific: `solverType`, `solverStepSize`, `communicationStep`, `internalFMUs`, `algebraicLoopCount`, etc.
  - `ModelStructure/Outputs` with `Unknown` entries for wrapper outputs
  - Uses `_derive_guid()` (MD5 hash of spec content) for deterministic GUIDs

**pyssp_standard equivalent:**
- `Fmi2ModelDescriptionXmlCodec` — can serialize `Fmi2ModelDescriptionDocument` to XML
- `ModelDescription` facade supports `mode="w"` for creating new documents
- But: no concept of tool annotations, custom `<CsFmuPackager>` elements, or `<InternalConnections>`

**Conclusion: Not replaceable.** The XML output is fundamentally a cs-fmu-packager artifact that embeds domain-specific metadata not in the FMI standard or pyssp_standard's scope.

## Current Pain Or Risk

- **Four private graph-algorithm functions maintained internally** that are functionally equivalent to a stable library module (`pyssp_standard.standard.operations.connection_graph`). This is maintenance burden (tests, edge cases, recursion-limit risk) with zero differentiation value.
- **Conversion layer in `fmu_reader.py`** (lines 71–103) manually maps between fork's typed dataclasses and project's custom dataclasses — ~30 lines of boilerplate that must stay in sync with fork API changes.
- **Hand-rolled ZIP assembly in `packager.py`** duplicates pyssp_standard's `FMU.create()` / `FMU.add_binary()` / `FMU.add_resource()` — but with specific deterministic-timestamp requirements that the library doesn't support.
- **Traceability gap**: Trace Chain 3 (algebraic loop handling) in `product-breakdown/traceability-map.md` references `mapper.md` Tarjan implementation — would need updating if algorithms are outsourced.
- **Dependency split-risk**: pyssp_standard is already a hard dependency (IMP-013), so any value not extracted from it is a missed opportunity.

## Proposed Improvement

### Recommendation A: Graph Algorithms — **REPLACE**

Replace `_build_adjacency_list`, `_tarjan_scc`, `_topological_sort` in `mapper.py` with calls to `pyssp_standard.standard.operations.connection_graph`.

**Adapter needed:**
```python
# Convert ResolvedConnection list to (source, target) pairs
conn_pairs = [(c.source_fmu, c.target_fmu) for c in resolved_connections]
# Compute execution order and SCCs
execution_order, scc_sets = connection_graph.compute_execution_order(conn_pairs)
```

**Impact on `build_mapping()`:**
- Lines 339–365 would change from:
  ```python
  adj = _build_adjacency_list(resolved_connections, fmu_ids)
  sccs = _tarjan_scc(adj)
  algebraic_loops = [...]  # build from sccs
  execution_order = _topological_sort(adj, [scc[:] for scc in sccs])
  ```
  to:
  ```python
  conn_pairs = [(c.source_fmu, c.target_fmu) for c in resolved_connections]
  execution_order, scc_sets = connection_graph.compute_execution_order(conn_pairs)
  algebraic_loops = [
      AlgebraicLoop(fmus=list(scc), connections=[...], iterations=..., tolerance=...)
      for scc in scc_sets
  ]
  ```

**Four functions removed:** `_build_adjacency_list`, `_tarjan_scc`, `_topological_sort` (and their unit tests in `test_mapper.py`).

### Recommendation B: FMI Dataclasses — **PARTIAL-ADOPT** (keep conversion layer)

Keep the conversion layer in `fmu_reader.py`. Full adoption would require:
- Refactoring all downstream consumers (`build_mapping`, `codegen/*`, `model_description.py`) to accept `Fmi2ModelDescriptionDocument` and `Fmi2ScalarVariable` instead of `FmuMetadata` and `ScalarVariable`
- Changes to `models.py` to deprecate or remove custom dataclasses
- This is a larger refactoring with high blast radius

**Defer** to a future candidate. The conversion layer is ~30 lines and well-encapsulated.

### Recommendation C: FMU Archive Creation — **PARTIAL-ADOPT** (with adapter)

Use `FMU.add_binary()` and `FMU.add_resource()` for standard directory entries, but maintain custom `_make_zip_info()`-style deterministic timestamps. Options:

1. **Hybrid approach**: Write modelDescription.xml and .so/.fmu files as before, but use `FMU` context manager or `zipfile.ZipFile` directly for the final archive. The project already has this — little benefit.
2. **FMU.create() with post-processing**: Create via `FMU.create()`, then re-open and fix timestamps. Adds I/O overhead.
3. **Accept non-deterministic timestamps**: Simplest change, but violates NFR-001 (reproducible artifacts).

**Recommendation**: Leave as-is unless NFR-001 is relaxed. The pyssp_standard ZIP layer adds I/O overhead (extract/repackage) without benefit for this use case.

### Recommendation D: Model Description Generation — **REJECT**

`generate_model_description()` is intrinsically project-specific (CS annotations). pyssp_standard cannot replace it.
