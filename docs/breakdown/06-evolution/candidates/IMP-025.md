## Current Pain Or Risk

- Dual-parsing in production: `fmu_reader.py` uses BOTH `pyssp_standard` and `lxml` for the same `modelDescription.xml` — pyssp_standard does not expose `valueReference`, `initial`, `start`, `unit` at the variable level, nor `ModelStructure` data.
- Hand-rolled ZIP in tests: `test_fmu_inspection.py`, `helpers.py`, `test_end_to_end.py` use raw `zipfile.ZipFile` for FMU creation — reimplementing what both libraries already provide.
- Hand-rolled ZIP in production: `packager.py` uses custom `_make_zip_info()` and `zipfile.ZipFile` for output FMU assembly.
- Missing `lxml` dependency declaration: `fmu_reader.py` imports `lxml` but `pyproject.toml` does not list it (transitive via `pyssp-standard` only — fragile).
- Test-identity ambiguity: Using `fmpy` as a reference parser changes what `test_fmu_inspection.py` actually tests.
- Parallel structure risk: Two libraries (`fmpy` tests + `pyssp_standard` production) providing the same FMU metadata access.

## Proposed Improvement

Dual assessment:

- (A) XML/ZIP parsing replacement: Evaluate where `fmpy` APIs (`read_model_description`, `create_zip_archive`, `create_fmu`, `generate_model_description`) and `pyssp_standard` APIs (`FMU` context manager, `ZIPFile.add_file_contents`, `ZIPFile.add_file`) could replace or reduce hand-rolled parsing/creation in each file.
- (B) Broader capability audit: Evaluate beyond XML access — schema validation (`fmpy.validation.validate_fmu`), FMU structure creation (`fmpy.template.create_fmu`), ZIP assembly (`fmpy.util.create_zip_archive`), SSP-level validation (pyssp_standard), FMI semantic checks, minimal FMU generation for tests (`fmpy.template.generate_model_description`).
- (C) jkCXf9X4 fork assessment: Evaluate whether the fork's version-routed typed dataclass architecture (Fmi2ScalarVariable, Fmi3ScalarVariable with value_reference/initial/start as first-class fields, Fmi2ModelStructure/Fmi3ModelStructure) could eliminate the lxml dual-parsing workaround in fmu_reader.py.

## Expected Benefit

- Consolidated library usage — reduce custom XML/ZIP maintenance
- Leverage FMPy's mature FMI XSD validation and semantic checks
- Simplify test FMU creation via `fmpy.template.create_fmu` or `fmpy.generate_model_description`
- Identify whether pyssp_standard gaps (no valueReference, no ModelStructure) could be filled by fmpy, or whether dual-parsing is permanent
- Resolve the missing `lxml` dependency gap

## Risk And Blast Radius

- Low-Moderate (evaluation phase, no implementation)
- Dual-library complexity — if evaluation endorses using BOTH fmpy and pyssp_standard for different things, the project gains two library dependencies for the same domain.
- fmpy maturity — fmpy is well-maintained (~579 stars, wide use) vs. pyssp_standard alpha (~3 stars).
- Test identity remains — any adoption of fmpy in tests must not replace what test_fmu_inspection.py is supposed to test (the project's own fmu_reader.py).
- IMP-013 continuity — if evaluation recommends shifting from pyssp_standard to fmpy in production, that contradicts the completed IMP-013 implementation.

### Architecture Notes

The fork restructures the model description layer into a version-routed architecture:
- `pyssp_standard/md.py` — facade with version routing to FMI 2.x or 3.x
- `pyssp_standard/standard/fmi2/model/model_description.py` — typed dataclasses for FMI 2.x
- `pyssp_standard/standard/fmi3/model/model_description.py` — typed dataclasses for FMI 3.x
- Both document classes have filter methods: `get()`, `inputs`, `outputs`, `parameters`
- Fork uses `Fmi3Unknown.value_reference: int` vs FMI2's `Fmi2Unknown.index: str` — proper FMI 3.0 support
- `Fmi3InterfaceAttributes` hierarchy (`Fmi3ModelExchange`, `Fmi3CoSimulation`, `Fmi3ScheduledExecution`) provides clean typed access to interface capabilities

### Impact Assessment

If the fork were adopted:
- **fmu_reader.py dual-parsing eliminated** — `valueReference`, `initial`, `start` become direct attributes on ScalarVariable; `ModelStructure` is a first-class dataclass
- **lxml import removed** — no need for manual XML traversal
- **Test helpers simplified** — typed dataclass constructors replace string-template XML + zipfile workarounds
- **FMI 3.0 support gained** — via version routing in md.py facade

### Risks

1. **Fork maintenance**: 0 stars, personal fork, `architecture_review` branch name suggests active development but unclear long-term support
2. **API compatibility**: The fork's API differs from upstream pyssp_standard; version-routed architecture changes import paths
3. **IMP-013 continuity**: Adopting this fork would reverse the upstream pyssp_standard dependency added in IMP-013
4. **Type_attributes dict for unit**: unit access still requires dict lookup — not as clean as other fields
5. **Branch naming**: `architecture_review` suggests the fork may be an experimental/draft branch, not a stable release

### Implementation Discoveries

- **Packaging fix required**: The fork's `setup.py` uses `distutils.core.setup` with `packages=['pyssp_standard']`, which does not include subpackages (`common/`, `standard/`). For `pip install` from git to work, the setup.py must use `setuptools.setup` with `find_packages()` and `__init__.py` must be added to `pyssp_standard/common/`, `pyssp_standard/standard/`, and `pyssp_standard/standard/common/`. The `package_data` must also include `schema/*/*.xsd` patterns. These fixes are applied in the local patched copy at `/tmp/pss_fix`.
- **`md.xml` property**: The fork's `ModelDescription.xml` property raises `RuntimeError` until `load_document()` is called. The work order instruction `doc = md.xml` is corrected to `doc = md.load_document()`.
- **Missing document fields**: `description`, `author`, `version` are not exposed as direct dataclass fields — accessed via `doc.root.attributes.get("description", "")`.
- **ModelExchange attributes**: No separate `Fmi2ModelExchange` dataclass; attributes are in `doc.interface_attributes` dict with XML attribute names as keys.
